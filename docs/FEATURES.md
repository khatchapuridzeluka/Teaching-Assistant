# Features in detail

The full description of every feature area: what it does, how it works and what is planned. The
[README](../README.md#features) has the one-line summary of each.

| Area | What it does | Status |
|---|---|---|
| **Classroom ingestion** | Connects a teacher's Google account (read-only OAuth), lists courses, assignments and submissions, and fetches turned-in work into stored versions (snapshots); unchanged submissions are skipped. The same fetch stores the assignment's instructions (task statement and attached files) as versions too, downloading them again only when they change. Every fetch also checks that the latest stored version of each submission and of the instructions is really on disk: missing files are downloaded again in place under their recorded names (not as a new version) and missing extracted code is rebuilt, reported in the fetch summary | Listing ✅ · fetch & versions ✅ · instructions stored ✅ |
| **Submission formats** | Zip/rar/7z archives of `.java` files, loose files, documents, images, or GitHub repository links | Drive files stored ✅ · zip/rar/7z/tar extraction ✅ (folders kept whether the archive separates them with / or, as Windows RAR files do, with \) · public GitHub repositories ✅: a link to a repository, branch or folder (`tree/…`, `blob/…`), pull request or commit is resolved to its current commit and that commit is downloaded as a zip (a pull request from a fork is downloaded from the fork) and extracted like an uploaded archive; the commit SHA is the version's fingerprint, so a new push becomes a new version and an unchanged repository downloads nothing; a private, renamed or deleted repository is recorded with the reason (*ask the student to make it public*) and picked up by a later fetch once it is public; a rate limit or network error skips the student until the next fetch; repositories over 100 MB are refused; a stored repository missing from disk is downloaded again from its commit · private repositories and pull-request diffs planned |
| **Sandboxed checks** | Compiles and runs student code in Docker (JDK 17–27), collecting compiler warnings, static analysis and test results before any AI judgment | Images ✅: `sandbox/java/Dockerfile` builds `ta-java:27` (first choice) and `ta-java:21` (fallback): a Temurin JDK with Checkstyle, PMD and SpotBugs (pinned versions, SHA-256 checked), an unprivileged user and a `/work` folder; checked to run locked down (no network, read-only, memory/CPU/process limits). See `sandbox/README.md` · port ✅: `ISandboxRunner` (Application) takes an image, the files and the steps to run (command, stdin, timeout, stop on failure) and returns each step's outcome (succeeded, failed, timed out, skipped), exit code and output; `SandboxUnavailableException` when Docker or the image is missing · runner ✅: `DockerSandboxRunner` (Infrastructure/Sandbox) drives the `docker` command line: it starts a fresh container per run from a local image (never pulled) with no network, a read-only file system with only `/work` and `/tmp` writable in memory, 512 MB memory, 1 CPU, 128 processes, no capabilities and the unprivileged user; streams the files into `/work` as tar; runs each step with `docker exec` under `timeout` (30 s per step and 2 minutes per run by default, so an endless loop is stopped inside the container) with stdin when given, keeps the first 64 KB of each output, skips the rest after a failed step marked stop-on-failure, and always removes the container. A missing image, a stopped Docker or a missing docker program raise `SandboxUnavailableException` with a plain message; a compile error or timeout is a normal step result. Limits are in the `Sandbox` configuration section · compile check ✅: every grading first compiles the version's `.java` files (`JavaBuildCheck`) in `ta-java:27` with `javac` (UTF-8; warnings for unchecked and raw generics, deprecated APIs, switch fall-through, static members used through an object, needless casts, constant division by zero, empty statements and equals without hashCode, at most 50; a byte order mark dropped first since javac rejects it), at most 30 s. Files are grouped into programs by the folder their packages start from (`JavaCompileUnits` in Domain), so several tasks side by side, each with its own `Main` and no package, compile separately instead of failing as duplicates. The result goes into the grading prompt as a `<build_and_test_results>` section just before the closing line (compiled, with how many warnings / did NOT compile with javac's messages, paths as in the submission / timed out), and `grading.md` tells the grader to treat it as fact (a compile error is a real mistake on its line, one per cause) and to open the review's Score section with a **Build:** line (compiled, with warnings, did not compile with the main cause, or timed out). Then Checkstyle reads all the Java files (it needs no compiling, so it runs even when compiling fails) with a short rule list in `Application/Checks/checkstyle.xml`, sent into the sandbox with each check: naming conventions, non-private fields (protected allowed), unused and redundant imports, missing braces, strings compared with ==, empty catch blocks, switch without default and simplifiable boolean logic; formatting and Javadoc are left out. After it PMD runs with its own short list in `Application/Checks/pmd.xml` (unclosed resources such as a `Scanner`, objects compared with ==, unused local variables, private fields and private methods, overly complex or deeply nested code, fields that should be local variables, strings built with += in a loop; what javac and Checkstyle already catch is left out), with the compiled classes on its classpath where compiling worked so it knows the types; PMD's exit codes 4 and 5 (findings, some files unparsable) count as finished. Its findings go into the same section as `path:line:column: message [Rule]` lines with the submission's paths (a file it cannot parse is counted in a note), and the grader is told they are evidence, not automatic deductions: the grading rules decide what costs points, repeats of one rule are one mistake, and the Build line adds "Checkstyle: N findings; PMD: N findings". PMD's findings come as `path:line: message [Rule]` lines in the same section. No Java files: no check and no section. Docker or the image missing: the grading goes on without the section. Each draft keeps `build_status` (Compiled, CompileFailed, TimedOut, Skipped, Unavailable; empty for older drafts), `build_output` (the compiler's messages or why it did not run), `style_findings` / `pmd_findings` (each tool's count; empty when it did not run) and `style_output` / `pmd_output` (their findings), also in the grading responses; the review card and the AI drafts page show a chip for the build (Compiled, Compiled with warnings, Did not compile, Compile timed out, Nothing to compile, Not compiled) and one each for Checkstyle and PMD (clean, N findings, not run), each with its messages folded below (open for a failed compile), and older drafts say they were read from the code only · running the program, console tests, SpotBugs and a per-assignment switch planned |
| **Rubric grading** | Claude grades against a layered rubric: base rubric → per-assignment extensions → the teacher's policy rules | First version ✅: "Grade with AI" sends one stored version (code, PDFs, images, including drawings inside the submitted archive; Word .docx as text plus the pictures embedded in it, such as code screenshots) with the assignment's stored instructions (saved by the fetch; no Classroom calls while grading) to Claude Opus 5.5 (`Anthropic:GradingModel`, effort medium, streamed with up to `Anthropic:GradingMaxTokens` = 64,000 output tokens, thinking included) as structured output: a Markdown review (score per task, feedback) plus a list of mistakes with fixed severity and category enums, the points each one takes off (0 for Style) and the file and lines they are on (checked against the code that was sent), and up to three **strengths**: specific skills the code shows were done well, such as a hard part of the task done right or work beyond it (never "it compiles" or general praise; empty only when nothing stands out), each with the same categories as mistakes, a one-sentence message and its lines. Strengths never change the score. Drafts graded before strengths existed have none. The code viewer marks each mistake with a coloured dot in the gutter and a tinted line and each strength in green, the message shows on hover, and clicking a mistake or strength in the list jumps to its line; reads the code only. Every grading is **saved as a draft** the moment it arrives (review text, score / max / bonus as numbers, mistakes as rows, the raw answer, model and instructions version), so a refresh never loses a paid grading; "Grade again" adds a new draft and the newest one is current, earlier ones stay pickable, and "Discard" throws one away (kept in the history). The assignment list marks a draft with its score and mistakes per severity, and "Saved drafts" in the ⋯ menu opens every saved draft of the assignment. The course's **AI drafts** page (sidebar) opens on an overview, to choose first: **by assignment** (each with its drafts, students, average AI score and major mistakes) or **by student** (across assignments), or all drafts in one list. Choosing one opens only that choice's drafts ("← Overview" goes back): a student's drafts across their assignments (narrowable to one of them), or an assignment's drafts for its students; "all drafts" has an assignment (top) and a student (below) dropdown. Filters are applied by the API; the list shows score, mistake dots and version; the selected draft opens next to its code (review, mistakes that jump to their lines, Discard, "Open in assignment"). Filters and the open draft are kept in the URL; on phones the filters become two dropdowns. First policy rules are built into the prompt: trivial issues (printed-text wording, comments, unused imports or variables) are listed as gray Style suggestions and cost no points; a variable or method name that differs from one the instructions specify costs 3 points each. **Review & approve** (**Edit report** once you saved one) opens a modal to correct the score and bonus, the Markdown feedback and every mistake (severity and category dropdowns, the points it takes off, editable message, reject / restore) and every strength (category, message, reject / restore; the modal adds up the kept mistakes' points next to the score, which stays yours to set); **Save** keeps it as your report in review, **Approve** makes it final. The report (one per draft, carrying the student, course and assignment so feedback and scores can be filtered per student directly) is stored next to the AI draft, which is never changed ("AI original" shows it again), and every mistake and strength records whether you kept, edited or rejected it, for later accuracy measurement and policy-rule suggestions; the submission shows your report (score, feedback, kept mistakes in the list and the code), the assignment list shows "In review" / "Approved", and approved reports leave the Review queue. **PDF export** ✅: the **PDF** button next to a draft (submission review and AI drafts page) downloads that grading as a report laid out like a Jira issue, generated on request and never stored: a breadcrumb and the assignment as the title, a notice unless it is approved, the review rendered from its Markdown (headings, the per-task score table, lists, inline code) and the mistakes and strengths as the same cards the app shows (a left border and label in the severity colour, the category, the points as a red pill, file:line; strengths with the thumbs-up) on the left, and a **Details** panel on the right (the app's status chip, student with initials, score / max and bonus, the AI's suggestion when your report differs, mistakes per severity with the app's severity dots, points deducted, strengths, turned-in, due, graded and approved dates), with the app's logo, colours, symbols and fonts; your report is used when you saved one (rejected mistakes and strengths left out), otherwise the AI draft. Built with QuestPDF (Community licence) and Markdig in Infrastructure, behind `IGradingDocumentRenderer`; the fonts are the UI's FiraGO, JetBrains Mono and Noto Sans Georgian (for Georgian names), converted to TTF from the frontend's Fontsource packages and embedded in the Infrastructure assembly (`Documents/Fonts`, OFL licences alongside), so the PDF looks the same on every machine and in the container. Nothing is sent to Classroom or the student · adding mistakes the AI missed planned · Rubric & policy page ✅ (every layer editable): the course page shows what the grader receives, in order: the built-in approach (six principles), course guidance (the teacher's own text per course, stored in `course_guidance` and edited in a modal on its tab; the grader gets it between the built-in principles and the rules, and an empty text removes it), your rules (stored in `policy_rules`, seeded with the two rules the grader used before, word for word: trivial issues cost nothing; a name the instructions fix costs 3 points per name; the same for every course, with an **Add rule** button, an edit icon that opens a modal with the title, what it covers, the effect (no deduction or −N points per …) and the text the grader gets, and a delete icon that only marks the rule deleted), each assignment's instructions, and assignment notes (stored per assignment in `assignment_notes`; the **Assignments** tab lists each assignment with its note count, and selecting one shows its numbered notes under its instructions, with an edit modal, soft delete and an **Add note** button; the grader gets an assignment's notes last, only when grading that assignment, and they win over everything above for it). It is one page (`/courses/{id}/rubric`) with five tabs kept in the URL (`?tab=approach`, `guidance`, `rules`, `assignments`, plus `&assignment={id}` for the selected assignment; the earlier per-layer addresses such as `/rubric/rules` redirect to them). **Overview** is a dashboard: a count per layer, the five layers in reading order with their scope (every course, this course, per assignment) and whether each is in use, a *Before you grade* checklist of what is in place, the principles, guidance and rules changed last, and each assignment's statement, files and note count. **Built-in approach** and **Your rules** are lists with a search box (rules can also be filtered by effect): a row shows two lines of the text the grader gets and opens to the whole text, **Expand all** opens every row, and a list of up to three rows starts open. The principles are stored in `grading_principles`, seeded with the six principles the grader used before, word for word; an **Add principle** button opens the same modal empty and adds the new principle last; each has an edit icon that opens a small modal with its title and the text the grader gets, and a delete icon that only marks it deleted after a confirmation; the numbers follow the remaining principles' order, and the next grading in every course uses the change. **Course guidance** shows the text and its length out of 4,000 characters, or an example when it is empty. **Assignments** joins the two per-assignment layers in one workspace: the assignments on the left (search, filters *With notes* and *No instructions*) and the selected one on the right with its instructions (statement, attached files, the stored version grading uses) and its notes. Each layer tab has a side panel with the layer's scope, what it is for and the reading order. **Preview brief** in the page header opens all five layers for one chosen assignment in the order the grader gets them, read-only. The grading prompt is built from the same rows (`GradingPromptSections`), so the page and the grader cannot drift apart |
| **Background jobs** | Long work runs in a queue instead of inside the HTTP request | First version ✅ for grading: "Grade with AI" queues a job (`202 Accepted`) after quick checks; a background worker inside the API claims it (Postgres `FOR UPDATE SKIP LOCKED`), runs up to 3 at once, retries temporary failures (model overloaded, Google down) after 30 s, 1 min, 2 min…, but not a model answer that was cut off at the length limit or refused, since asking again gives the same result and costs the same, recovers jobs whose worker stopped (10-minute lease with a heartbeat), and supports cancel. One active job per version (a double-click returns the same job). The page shows Queued… / Grading… and the draft appears when ready, even after leaving or refreshing the page. A message bar at the top follows each grading you start on any page (queued → started → finished with an **Open draft** link, or failed / retrying); it polls `GET /jobs/{jobId}` every 2 s and survives a page refresh. The direct synchronous grade endpoint is kept. The workspace **System** page shows the queue: running and queued now, succeeded / failed / canceled in the last 24 hours, and the 200 most recent jobs filterable by kind of work (Single grading, Grade all, Grade student, Fetch student's work, Common mistakes, Evaluation run, Evaluation grading, Fetch, Course sync, Re-extract) and by status, each with the student, assignment and version, attempts, how long it waited or took, and its error; queued or running jobs can be canceled and failed or canceled ones retried (queued again as a new job). Jobs that are not about one student (Grade all, Common mistakes, …) show an icon for their kind of work, and clicking any job (or **Details**) opens a popup explaining in plain words what that kind of job does, who and what it was for, its status, attempts, error, when it was queued, started and finished with how long it waited and ran, and its result with links (open the draft, the Common mistakes page, or each grading of a Grade all / Grade student); it updates while the job runs and can cancel or retry it. It refreshes every 2 s while something runs. Every Claude call (grading, agent chat, model check) is recorded in `model_calls` by a wrapper around `ILanguageModel`: purpose, requested and answering model (the fallback shows), input / output / cache-read / cache-write tokens, duration, success or the error, and for gradings the course, assignment and version; only this metadata is stored, never prompts, code, answers or names, and a failure to record never affects the call itself. The System page's **Model usage** tab shows it for the last 7 / 30 / 90 days, for all work or one kind of work (Single grading, Grade all, Ask agent, model check; gradings started by a Grade all are recorded under their own purpose), with the per-purpose table always showing the full picture: per grading the average prompt and output tokens, the share of the prompt read from the cache and the average time; a tokens-per-day chart (prompt not cached, prompt from cache, output; with a per-day table); totals per purpose (AI grading, Ask agent, model check) with failures; and the recent calls with student, assignment, tokens, duration, error and the answering model (marked when the fallback answered). Tokens only, no prices yet. **Grade all with AI** (assignment page) queues one parent job with a child grading per student: each student's latest stored version, skipping students whose version already has a draft that is not discarded (unless **Also grade the ones that already have a draft** is ticked in the confirmation dialog, which the student profile's **Grade all assignments** dialog has too: then they are graded again, the new draft becoming current and the earlier one staying in the history), students already queued, students without stored work and failed fetches (problems such as missing instructions are listed by name); only one grade-all per assignment runs at a time. The parent makes no model call; it tracks its children (N of M done) and finishes with them, as Failed when any child failed; canceling it cancels its unfinished children, retrying it grades the students who still have no draft, and the worker's recovery pass re-checks open parents so simultaneous finishes can't leave one stuck. On the System page it is one row with a progress bar that expands into the students' gradings. **Grade all assignments with AI** on a student's profile does the same for one student across the course, in two background steps under one *Grade student* parent: first a *Fetch student's work* job downloads, read-only from Google Classroom, every assignment the student turned in (a failed fetch of one assignment is listed and the rest go on), then it queues one grading per assignment that now has stored work and no draft that is not discarded (assignments never turned in are left out); each grading is filed under its own assignment, the fetch job's result says how much was fetched and queued, and problems are listed by assignment title. Retrying the fetch alone is not possible; retry the *Grade student* parent. Fetching an assignment, syncing a course and re-extracting run on the same queue |
| **Automated tests** | The same test cases for every student, connected to each student's own class names by an adapter, with results given to the grader as evidence (design in `docs/PRODUCT.md`) | First step ✅: the assignment page's **Tests** view (List / Board / Tests) has **Create test cases**: a form for the test style (console or class design), what to cover (normal, boundaries, invalid input, large inputs, concurrency), how many, a focus, "don't test" and an optional reference solution (.java files). One background job (`GenerateTests`, one paid call to `Anthropic:GradingModel` at effort medium) sends the stored instructions, the settings, the course guidance, grading policy and assignment notes and the reference solution (never student work or names) and stores the answer as a new draft version: the requirements found (code numbers them and counts how many cases check each; a testable one without a test shows in red), the neutral interface for class-design tests, and the cases with steps and expected results (each behaviour is checked through the method that answers it, such as `size()` and `get(i)`, one value per check; the whole object as text, such as `toString`, only in cases for a requirement about that format). **Generate again** makes the next version. Editing and approving ✅: every requirement, the interface and every case can be edited inline, cases added, duplicated and deleted, requirements added and deleted (their references go with them); coverage updates as you edit. **Save changes** edits a draft in place; editing an approved set saves a new draft version while the approved one stays in use. **Approve** marks the newest version as the one gradings will use; only the newest version can be edited or approved. Requirements and cases are renumbered (R1…, T1…) on every save. Test code ✅: approving a class-design set queues a `GenerateTestCode` job (one paid call; also **Write again** on the **Test code** card) that turns the approved cases into one JUnit 6 class, `AssignmentTests`, calling only the neutral interface through `new StudentAdapter()` and grouping each case's checks in `assertAll` so every failed check is reported, not only the first, plus a placeholder `StudentAdapter` whose methods only throw; the sandbox compiles the interface, the placeholder and the tests together against the image's JUnit jar and the card shows the code and **Compiles** / **Doesn't compile** (with the compiler errors) / **Not compiled** (no sandbox, or an image built before JUnit was added). The code is stored with the approved version. Test runs ✅: the **Test results** card lists every student's latest stored version with a **Run** button (one `RunTests` job for that version; **Run for everyone** queues one per student). Each run compiles the student's code alone first (a compile error stops there, with no AI call), then writes the student's `StudentAdapter` with `Anthropic:AdapterModel` (Claude Sonnet 5.5 by default; the interface, the testable requirements and the student's code, never the name; the adapter only translates names and throws "not implemented" for what the student never wrote) or reuses the stored adapter when the interface is unchanged, compiles everything with the shared `AssignmentTests` and runs it with the JUnit console, reading the XML report per case: passed, failed (with the assertion message, or the exception, or "did not finish within 5 seconds"), not implemented, or did not run. An adapter that does not compile gets one repair attempt with the compiler errors; if it still fails the run is an adapter problem that never counts against the student. Results are stored per version in `test_runs` and shown as a students × cases matrix with the hardest case, the failure messages and each student's adapter. **Write adapter again** in a student's run detail ignores the stored adapter, writes a new one (one small paid call) and runs the tests again, for when an adapter maps the student's code wrongly (`newAdapter=true` on the run endpoint). In grading ✅: when the assignment has an approved class-design set with test code, every grading (single, Grade all, Try with model, evaluation runs) first takes that version's latest stored run for the set or runs the tests itself (`TestRunner`; adapter reused when it can be, so usually no extra AI call) and adds an `<automated_tests>` section just before the closing line: the set's version, how many cases passed, the requirements the cases check, and every case with its outcome, plus the steps, expected result and failure message for the ones that did not pass. `grading.md` tells the grader the results are facts but evidence, not the score: one mistake per cause on its lines (several cases failing for one cause, such as a toString format, cost what that one problem is worth), the case ids in the message, "not implemented" checked against the code, and "Tests: N of M passed" on the Score line. The draft's sent list records `Tests: version N, X of Y passed`, or that the tests were not run (the code does not compile) or not used (the adapter did not fit, which never counts against the student). No approved set, only a draft, no Docker or no Java files: the grading goes on without tests. |
| **Batch calibration** | Calibrates scores across the class and clusters common mistakes, so one explanation covers many students | Common mistakes ✅: the course's **Common mistakes** page analyzes one assignment as a queued job: the assignment's instructions (the same files grading uses), each student's draft score as S1, S2, … and every mistake of the current drafts (your report's version where one exists, rejected ones left out) go to the AI in one call, mistakes grouped by severity, numbered and tagged with their anonymous student, with category, points and location but no names; the AI writes an overview of up to 200 words of how the class managed the homework (main idea understood, careless blunders versus misunderstandings, what to revisit) plus a separate **For the next lecture** paragraph (up to 100 words: the one to three topics to stress, why, and what to show or practise) and groups the mistakes by meaning with a title and a class-wide explanation per group; the page shows the overview first, then total mistakes and mistakes per level with charts (levels, students affected per group), then all mistakes by group; code checks the answer (each mistake in one group, unknown numbers ignored, the rest kept as *Not grouped*) and counts students affected (and %), average points and severity per group, sorted by students affected. You edit and approve one explanation per group (the AI's text is kept) and open each student's mistake from the group. Every analysis is stored; the page shows the latest · score calibration planned |
| **Evaluation** | How often the AI's drafts agree with the teacher's final decisions | ✅ the workspace **Evaluation** page compares every **approved** report with the AI draft it was made from (a report whose draft was later discarded, for example because another draft of the submission was approved, and unreviewed drafts never count), across all courses or one: score accuracy (100 minus the average gap in points per 100, so 97.8% when the AI is off by 2.2 points per 100 on average, also per model), how many reports are within ±5 points per 100 of yours, the average gap and which way the AI leans (more lenient or stricter; under 1 point per 100 it says there is no real lean), mistakes confirmed (kept or edited vs. rejected) by the category and severity the AI chose, how often and how much you changed a mistake's points, strengths kept, the AI and your report against the grade returned in Classroom (an independent check made before these drafts), the same per model (to compare models after regrading the same submissions), and every report largest gap first with a link to its draft. Charts: AI vs. your score per report, how far off in 5-point steps, decisions by category and severity. **Discarded drafts** are counted and listed apart: discarding asks why (*Poor grading*, which counts against the AI; *Wrong version or files*; *Not needed*; *Other*) with an optional note of up to 500 characters, approving a draft sets the submission's other drafts aside as *Another draft approved* automatically, and both are stored on the draft (`discard_reason`, `discard_note`). The page shows the drafts *discarded as poor* next to the approved reports, the count per reason, per model, and every discarded draft with its student, assignment, AI score, mistakes, reason and note (the automatic ones on request), each opening the draft; a discarded draft shows its reason and note on the AI drafts page too. Counted in code by `DraftComparison` (Domain) and `EvaluationService` from stored data; no model is called. **Model comparison** (bottom of the page): **Run evaluation** picks any of `claude-fable-5-2`, `claude-opus-5-5`, `claude-sonnet-5-5` and `claude-haiku-5-5` and grades every approved report's submission version again on the side with each chosen model (the same prompt, rubric, policy and compile check as a real grading, the model chosen per call), as an *Evaluation run* parent job with one *Evaluation grading* child per report × model (retried like gradings). The results are stored apart in `evaluation_runs` and `evaluation_run_results` (score, bonus, mistakes, build status, answering model, time or error) and never become drafts, so the drafts, reports, profiles and the comparison above are untouched. Per model, from its newest result for each approved report, compared in code by `RunComparison` (Domain) with your report: score accuracy, within ±5, leaning, your kept mistakes it found again (same file and overlapping lines ±1, or the same category for a whole-submission mistake), rejected mistakes it repeated, mistakes not in your report, average time per grading and failures; the page follows a running run's progress. **Graded by** at the top of the page switches the whole page between *Your reviewed drafts* and any model with side gradings (kept in the URL as `?model=`): for a model every number and chart is recomputed from its newest side grading per approved report against your report (reports it has not graded yet are left out and said so): score accuracy, within ±5, leaning, the score chart and histogram, *Your mistakes found* (of the mistakes you kept), *Rejected ones repeated*, *Not in your report*, your kept mistakes by category and severity as found vs. missed, the Classroom check and the report-by-report table; the per-model and discarded-draft cards belong to drafts and are left out. Its calls are recorded under their own purpose, *Evaluation run*. **Try with model** (next to *Grade with AI* on a student's submission) grades the shown version once with a chosen model, exactly like a draft, and shows the answer in place of the draft (score next to the current draft's, review, build result, mistakes and strengths marked in the code) until **Close try**; it is never saved and never counts in the evaluation, and its calls are recorded under *Try with model* · adding mistakes the AI missed (for recall) planned |

| **Teacher UI** | A top bar holds the workspace pages (**Home**, **Review queue** with the number of waiting drafts, **Evaluation**, **System** with a live count of queued and running jobs), a **Jump to…** palette (Ctrl+K: pages, courses, and the open course's assignments and students; it only navigates), the Google Classroom status, Settings and Ask agent. **Home** opens with what is waiting for you (drafts to review, turned-in work without a draft, running and failed jobs), one card per course (assignments, drafts to review, next deadline, shortcuts), the oldest drafts of the queue and how a grade is made.
